# ADR-001: Model Egress Gateway Architecture & Ingress Isolation
## Status: Accepted

## 1. Context & Enterprise Problem Statement
The `governed-contract-compliance-agent` processes sensitive financial invoices and legal contracts (MSAs/SOWs) while interacting with external foundation model APIs[span_37](start_span)[span_37](end_span)[span_38](start_span)[span_38](end_span). Allowing application runtime code to call OpenAI, Anthropic, or Bedrock endpoints directly creates four enterprise risks:
1. **Unbounded Token Spend:** No hard budget caps or cost-center attribution across ingestion, reconciliation, and evaluation workloads[span_39](start_span)[span_39](end_span)[span_40](start_span)[span_40](end_span).
2. **Provider Lock-In & Outage Fragility:** Hardcoded SDK dependencies prevent seamless failover during provider rate-limiting (`429`) or regional outages[span_41](start_span)[span_41](end_span)[span_42](start_span)[span_42](end_span).
3. **Redundant Inference Latency & Cost:** Repeated compliance checks against identical MSA clauses incur full LLM latency and token costs without semantic caching[span_43](start_span)[span_43](end_span)[span_44](start_span)[span_44](end_span).
4. **Boundary Confusion:** Mixing external client ingress concerns (user OAuth/JWT validation) with outbound model egress concerns (provider API keys and PII scrubbing)[span_45](start_span)[span_45](end_span)[span_46](start_span)[span_46](end_span).

## 2. Decision Drivers
- Cost/token economics, per-cost-center attribution, and model provider decoupling[span_47](start_span)[span_47](end_span)[span_48](start_span)[span_48](end_span)
- Latency SLAs (`p50 < 2.5s`, `p95 < 6.0s`) via semantic caching and model tiering[span_49](start_span)[span_49](end_span)[span_50](start_span)[span_50](end_span)
- Zero-Trust security: zero external provider API keys stored inside the Python agent runtime
- Seamless extensibility to multi-client virtual keys and per-tenant spend caps in future iterations

## 3. Considered Options
- **Option A: Direct Provider SDKs (`openai` / `anthropic`) inside Python Runtime**
  - *Pros:* Minimal initial setup; zero extra network hop.
  - *Cons:* Tightly couples business logic to vendor APIs; requires custom retry, budget, caching, and telemetry code inside the agent.
- **Option B: Centralized Enterprise AI Gateway (`LiteLLM Proxy`) Decoupled from Client Ingress**
  - *Pros:* Exposes a unified OpenAI-compatible internal endpoint; enforces virtual API key spend limits, dynamic routing (cheap models for extraction, frontier models for reconciliation), Redis semantic caching, and automated fallback chains out of the box[span_51](start_span)[span_51](end_span)[span_52](start_span)[span_52](end_span)[span_53](start_span)[span_53](end_span).
  - *Cons:* Adds one local/internal network hop (`~2–5ms`) and requires operating a proxy container and PostgreSQL/Redis backing store[span_54](start_span)[span_54](end_span).

## 4. Decision Outcome
We select **Option B: Centralized Enterprise AI Gateway (`LiteLLM Proxy`)** strictly separated from client ingress[span_55](start_span)[span_55](end_span)[span_56](start_span)[span_56](end_span).
- All outbound LLM and embedding requests from `src/gateway/`, `src/ingestion/`, and `src/rag/` must target the internal `LiteLLM Proxy` endpoint (`http://localhost:4000` locally) using scoped virtual keys.
- **Dynamic Routing:** High-volume structured extraction tasks route to fast/low-cost models, while complex multi-clause contract reconciliation routes to high-reasoning frontier models[span_57](start_span)[span_57](end_span)[span_58](start_span)[span_58](end_span).
- **Semantic Caching:** Backed by Redis to serve repeated clause lookups within SLA targets[span_59](start_span)[span_59](end_span)[span_60](start_span)[span_60](end_span).

## 5. Consequences & Trade-Off Mitigations
- **Positive Impacts:**
  - Complete decoupling of agent code from underlying model vendors[span_61](start_span)[span_61](end_span)[span_62](start_span)[span_62](end_span).
  - 100% token and cost attribution per workflow/cost-center from day one[span_63](start_span)[span_63](end_span).
  - Built-in path to multi-client isolation via per-tenant virtual keys and rate limits.
- **Negative Impacts & Mitigations:**
  - *Single Point of Failure Risk:* Mitigated in production via stateless horizontal scaling of LiteLLM containers behind an internal load balancer and configured multi-provider fallback chains[span_64](start_span)[span_64](end_span)[span_65](start_span)[span_65](end_span).
  - *Added Local Infrastructure:* Mitigated via deterministic `docker-compose.yml` orchestration alongside PostgreSQL (`pgvector`) and Redis[span_66](start_span)[span_66](end_span)[span_67](start_span)[span_67](end_span).
