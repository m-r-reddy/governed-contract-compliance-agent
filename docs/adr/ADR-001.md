# ADR-001: Model Egress Gateway Architecture & Ingress Isolation
## Status: Accepted

## 1. Context & Enterprise Problem Statement
The `governed-contract-compliance-agent` processes sensitive financial invoices and legal contracts (MSAs/SOWs) while interacting with external foundation model APIs. Allowing application runtime code to call OpenAI, Anthropic, or Bedrock endpoints directly creates four enterprise risks:
1. **Unbounded Token Spend:** No hard budget caps or cost-center attribution across ingestion, reconciliation, and evaluation workloads.
2. **Provider Lock-In & Outage Fragility:** Hardcoded SDK dependencies prevent seamless failover during provider rate-limiting (`429`) or regional outages.
3. **Redundant Inference Latency & Cost:** Repeated compliance checks against identical MSA clauses incur full LLM latency and token costs without semantic caching.
4. **Boundary Confusion:** Mixing external client ingress concerns (user OAuth/JWT validation) with outbound model egress concerns (provider API keys and PII scrubbing).

## 2. Decision Drivers
- Cost/token economics, per-cost-center attribution, and model provider decoupling
- Latency SLAs (`p50 < 2.5s`, `p95 < 6.0s`) via semantic caching and model tiering
- Zero-Trust security: zero external provider API keys stored inside the Python agent runtime
- Seamless extensibility to multi-client virtual keys and per-tenant spend caps in future iterations

## 3. Considered Options
- **Option A: Direct Provider SDKs (`openai` / `anthropic`) inside Python Runtime**
  - *Pros:* Minimal initial setup; zero extra network hop.
  - *Cons:* Tightly couples business logic to vendor APIs; requires custom retry, budget, caching, and telemetry code inside the agent.
- **Option B: Centralized Enterprise AI Gateway (`LiteLLM Proxy`) Decoupled from Client Ingress**
  - *Pros:* Exposes a unified OpenAI-compatible internal endpoint; enforces virtual API key spend limits, dynamic routing (cheap models for extraction, frontier models for reconciliation), Redis semantic caching, and automated fallback chains out of the box.
  - *Cons:* Adds one local/internal network hop (`~2–5ms`) and requires operating a proxy container and PostgreSQL/Redis backing store.

## 4. Decision Outcome
We select **Option B: Centralized Enterprise AI Gateway (`LiteLLM Proxy`)** strictly separated from client ingress.
- All outbound LLM and embedding requests from `src/gateway/`, `src/ingestion/`, and `src/rag/` must target the internal `LiteLLM Proxy` endpoint (`http://localhost:4000` locally) using scoped virtual keys.
- **Dynamic Routing:** High-volume structured extraction tasks route to fast/low-cost models, while complex multi-clause contract reconciliation routes to high-reasoning frontier models.
- **Semantic Caching:** Backed by Redis to serve repeated clause lookups within SLA targets.

## 5. Consequences & Trade-Off Mitigations
- **Positive Impacts:**
  - Complete decoupling of agent code from underlying model vendors.
  - 100% token and cost attribution per workflow/cost-center from day one.
  - Built-in path to multi-client isolation via per-tenant virtual keys and rate limits.
- **Negative Impacts & Mitigations:**
  - *Single Point of Failure Risk:* Mitigated in production via stateless horizontal scaling of LiteLLM containers behind an internal load balancer and configured multi-provider fallback chains.
  - *Added Local Infrastructure:* Mitigated via deterministic `docker-compose.yml` orchestration alongside PostgreSQL (`pgvector`) and Redis.
